# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```
npm run dev       # start Vite dev server
npm run build     # production build to dist/
npm run preview   # preview the production build
npm run lint      # oxlint
```

There is no test suite configured in this project.

Requires `VITE_GEMINI_API_KEY` in `.env` (see `.env` — currently blank locally) for any Gemini-backed feature (AI Assistant incl. its `/baholash` scoring, AI Taqqoslash, Xulosalar tekshirish, Expert Assistant's Q&A widget) to work.

## Architecture

React 19 + Vite SPA, Tailwind v4 (via `@tailwindcss/vite` plugin, no separate config file), routed with `react-router-dom` (`BrowserRouter`, all routes declared in `src/App.jsx`). Netlify hosts it (`netlify.toml` — SPA fallback rewrites `/*` to `/index.html`).

`src/App.jsx` special-cases `/taqdimot`: it renders `PresentationPage` standalone (no `Sidebar`/layout chrome), checked via `location.pathname` before the normal layout+`Routes` tree. Every other route renders inside the `Sidebar` + flex layout.

### Pages (`src/pages/`) and what they do
- `DashboardPage` — home (`/`); KPI cards and quick-access lists (urgent arizalar, pending xulosalar) plus a `DashboardTab` company-rating summary and a pollution-by-viloyat chart, all derived client-side from `dataUtils.js` + the `data/` seed modules.
- `CompaniesPage` (`/loyihachilar`) — lists ecological-expertise consultants aggregated from `public/new-companies.json`, sortable/searchable/paginated via `src/utils/dataUtils.js`.
- `CompanyDetailPage` (`/company/:id`) — a single consultant's project history.
- `AiTaqqoslashPage` (`/ai-taqqoslash`) — pick an enterprise (`data/taqqoslashKorxonalar.js`), drag its "hozirgi"/"avvalgi" arizalar into two drop slots, and run `compareArizalar` (in `utils/gemini.js`) to find inconsistencies between the two filings.
- `ArizalarPage` (`/arizalar`) — list of incoming applications backed by `src/data/arizalar.js` / `arizaFiles.js`.
- `XulosalarPage` (`/xulosalar`) — list of expert-written conclusions (`data/xulosalar.js` / `xulosaFiles.js`) awaiting AI-assisted review via `XulosaCheckModal` (uses `utils/xulosaGemini.js`); accept/reject decisions are persisted per `ariza_raqami` in `localStorage` under the key `xulosa-reviews` — `DashboardPage` reads the same key to exclude reviewed items from its "pending" counts, so keep the two in sync if this changes.
- `AiAssistantPage` (`/ai-assistant`, top nav item) — chat assistant grounded on `public/234-qaror.pdf` (`utils/assistant.js`), merged with the standalone document-scoring flow: a paperclip button attaches a PDF and a `/baholash` button (next to Send) pushes an inline `AiEvaluationPanel` (`initialFile`, `autoStart`) into the chat as its own turn. Chat turns and evaluation turns share one ordered `items` list in component state; only `kind: 'text'` items are sent as history to `sendAssistantMessage` — evaluation turns render/run independently and aren't part of the Gemini chat history. There is no separate `/ai-baholash` route anymore (the old `AiPage` was removed) — `AiEvaluationPanel` is still used standalone inside `AiEvaluationModal` for the `ArizalarPage` "Tekshirish" flow.
- `ExpertAssistantPage` (`/expert-assistant`, sidebar entry right after Arizalar) — two internal views toggled by local state (no sub-route): `ArizaListView` reuses the same `ARIZALAR`/`ARIZA_FILES` data and table layout as `ArizalarPage` (search included) but with a "Xulosa yozish" action instead of "Tekshirish"; picking a row switches to `XulosaEditorView`, a plain "Word-like" drafting surface (title input + textarea styled as a paper sheet, no rich-text formatting) keyed by `ariza.orderNum` so switching arizalar discards the previous draft rather than leaking it into the new one. `ExpertQuestionWidget` (`src/components/ExpertQuestionWidget.jsx`) is rendered only inside the editor view: a floating chat-bubble button opens a small Q&A panel reusing `sendAssistantMessage`, grounded not just on 234-qaror but also on the selected ariza's own documents (`arizaSource` prop → `buildDocumentParts`, fetched once per widget instance and cached in a ref, not re-fetched per message) and a republic-wide emissions aggregate (`emissionsAware` prop → `utils/emissionsSummary.js`) — so questions like "loyihada nima ko'zda tutilgan" or "Toshkent shahriga qancha azot dioksidi chiqadi" both get answered. `AiAssistantPage`'s own widget usage doesn't set these props, so its chat stays 234-qaror-only.
- `XaritaPage` (`/xarita`) — interactive Leaflet map of Uzbekistan with region → district drill-down, enterprise markers, and a live wind-velocity overlay.
- `PresentationPage` (`/taqdimot`, opened via a new tab from the sidebar) — a standalone, sidebar-free slideshow pitching each feature (per-feature multi-page mini-decks defined in a `functionDetails` map inside the component); purely presentational, no data fetching beyond its own static copy.

### Data layer: static JSON/JS, not a backend API
There is no application backend. All "data" is either:
- static files under `public/` (`new-companies.json`, PDFs in `public/arizalar/`, `234-qaror.pdf`) fetched at runtime with `fetch()`, or
- hand-authored JS/JSON modules under `src/data/` and `src/utils/uzbekistanGeoJson/data/` (GeoJSON split per region, one file per viloyat, aggregated by `data/regions.js`).

`src/utils/dataUtils.js` loads and caches `public/new-companies.json` once (`_cache`) and derives everything (company aggregates, dashboard chart series, loyihachi rating tiers) from that single flat record array client-side — there is no server-side aggregation. `new-companies.json` is a bare top-level array (not wrapped in a `{ companies: [...] }` object). Records use Cyrillic Uzbek fields transliterated to Latin via the `toLatin()` map in the same file; reuse that helper rather than adding a new transliteration table.

Enterprise/pollution data (`data/korxonalar.js`, `data/tashkentKorxonalari.js`) is explicitly seed/placeholder data — each record's `hudud` (polygon) and `tashlanmalar` (emissions by category) were hand-built to line up with the real district GeoJSON centroids, not sourced from a live monitoring feed. `data/xaritaFakeData.json` is a leftover from an earlier iteration of the map and is no longer read by `XaritaPage`.

### Gemini integration (four independent call sites, all client-side)
All use `@google/genai` directly from the browser with `import.meta.env.VITE_GEMINI_API_KEY` — no proxy/backend. `src/utils/gemini.js` holds shared helpers (`sourceToArrayBuffer`, `arrayBufferToBase64`, `detectMimeType`, `buildDocumentParts`) reused by the other call sites — don't duplicate them.
- `src/utils/gemini.js` (`checkArizaAcceptance`) — the gate `AiEvaluationPanel` runs *before* scoring: checks the ariza + its attachments against the 17 formal-completeness requirements in `src/utils/arizaQabulPrompt.js` (`ARIZA_QABUL_SYSTEM_PROMPT`/`ARIZA_QABUL_USER_MESSAGE`, also Resolution No. 234-derived but a pass/fail checklist, not the 100-point rubric). `AiEvaluationPanel` only calls `evaluateProject` after this stage returns `xulosa.qabul_qilinishi_mumkin: true` (user can still force-proceed via the "Loyihani baholashga o'tish" button in `AcceptanceView`).
- `src/utils/gemini.js` (`evaluateProject`) — scores an uploaded/linked ariza PDF against the rubric in `src/utils/prompt.js` (`SYSTEM_PROMPT`/`USER_MESSAGE`, written in Uzbek, encodes the actual scoring rules from Resolution No. 234). It pulls PDF link-annotations out of the ariza via `src/utils/pdfLinks.js` (pdfjs-dist) to find and attach referenced project documents before sending everything to `gemini-2.5-flash`. The model's own `total_score` is not trusted — `normalizeScore()` recomputes it from `evaluation_matrix` and hard-caps it at 95 (100 is defined as unreachable by design).
- `src/utils/gemini.js` (`compareArizalar`) — same `buildDocumentParts` pipeline run twice (once per ariza), sent together with the rubric in `src/utils/comparePrompt.js` (`COMPARE_SYSTEM_PROMPT`/`COMPARE_USER_MESSAGE`) to flag mismatches between two filings from the same enterprise (e.g. current vs. prior submission).
- `src/utils/xulosaGemini.js` (`evaluateXulosa`) — checks a single expert-written xulosa PDF against `src/utils/xulosaPrompt.js` (`XULOSA_SYSTEM_PROMPT`/`XULOSA_USER_MESSAGE`); explicitly injects the real device date (`formatToday()`) into the prompt so date-comparison checks don't fall back to the model's stale training cutoff.
- `src/utils/assistant.js` (`sendAssistantMessage(history, message, context)`) — a Q&A assistant always grounded on `public/234-qaror.pdf` (uploaded once via the Files API, `ai.files.upload`, memoized in a module-level promise, polled until `ACTIVE`) via a synthetic user/model priming turn, optionally extended by `context.projectParts` (a `buildDocumentParts()` result — primes a second synthetic turn with a specific ariza + its linked project documents) and/or `context.includeEmissions` (primes a third turn with `utils/emissionsSummary.js`'s text block) before appending real history. `ExpertQuestionWidget` is the only caller that passes these; `AiAssistantPage` calls it with no `context` (234-qaror only). The system instruction enforces strict language/script mirroring (Uzbek Latin vs Cyrillic vs Russian) matching the user's own input, and is deliberately phrased around "whatever sources were provided in this conversation" rather than hardcoding "only 234-qaror" — preserve both behaviors if touching the prompt.
- `src/utils/emissionsSummary.js` (`buildEmissionsSummary`) — aggregates the ~929 raw enterprise records across `data/korxonalar.js` + `data/tashkentKorxonalari.js` (~53k lines combined) into a compact per-viloyat/per-category/per-modda sum (14 viloyat groups), memoized in a module-level `cached` string on first call. Exists so `sendAssistantMessage`'s emissions grounding stays cheap — never pass the raw seed arrays into a prompt directly.

When editing any of these prompts, keep the JSON output contract intact — UI components (`AiEvaluationPanel`, `AiEvaluationModal`, `AiTaqqoslashPage`, `XulosaCheckModal`) parse the model's JSON response directly.

### Map page (`XaritaPage.jsx`)
Single large (~2400 line) component ported from a separate reference project (`geojson_uz/`, gitignored, not part of this repo). It composes `react-leaflet` primitives with local helper components (`MapClickHandler`, `MapZoomController`, `MapAutoResize`) and drives region/district drill-down from the GeoJSON data modules plus enterprise data from `data/korxonalar.js`/`data/tashkentKorxonalari.js`. `MapAutoResize` exists specifically because `MapContainer` remounts on drill-down navigation inside a flex layout and needs a forced `invalidateSize()`.

Wind overlay: `src/utils/leafletGlobalSetup.js` must be imported before `leaflet-velocity` anywhere it's used — `leaflet-velocity` is a UMD build that expects a global `window.L`, not an ES import, so this module stashes `leaflet`'s import onto `window.L` as a side effect. `src/utils/wind.js` fetches a coarse lat/lon wind grid for the Uzbekistan region from Open-Meteo (no API key required) and reshapes it into the GRIB2-style U/V grid `leaflet-velocity` expects; results are memoized in a module-level cache (`CACHE_TTL_MS`) with in-flight request dedup, since drill-down remounts and React StrictMode's double-invoke would otherwise trigger duplicate requests and hit Open-Meteo's rate limit. `src/utils/windColorScale.js` supplies the color ramp for the velocity layer.

Extra map layers (forest fund, water reservoirs, sanitary zones, protected areas, etc.) are pre-converted from source KMZ files, not fetched live: `kmz-source/*.kmz` (gitignored-scale, checked in) is run through one-off Node scripts (`node scripts/convert-kmz-to-geojson.mjs` for the per-region forest-fund layers, `node scripts/convert-extra-layers.mjs` for republic-wide layers) into `public/data/`, which `XaritaPage` then `fetch()`s at runtime. `ORMON_REGION_KEYS` lists which viloyats have forest-fund data (`public/data/ormon/<key>.json`); `EXTRA_LAYERS` (further down the same file) lists the republic-wide layers, each keyed to a `public/data/<key>.json` produced by `convert-extra-layers.mjs`'s `LAYERS` array — adding a new KMZ-derived layer means adding an entry to both `LAYERS` (source file, output key, `keepKeys` field map) and `EXTRA_LAYERS` (display label/color), then re-running the script. `EXTRA_FIELD_LABELS` maps the `keepKeys` output field names to human-readable Uzbek popup labels.

### Language
UI copy, data field values, and all Gemini prompts are in Uzbek (mix of Latin/Cyrillic script depending on context) — match the existing script/language when adding user-facing strings or model instructions rather than defaulting to English.
